Installation

A binary that brings its own deployment

The installer downloads one binary and asks it for everything else. The binary embeds its own deployment files, so configuration and code can never disagree about versions: there is no second download to fall out of step with.

On a machine of its own

For a VPS or a Raspberry Pi 5 (Debian 13 / Raspberry Pi OS, amd64 or arm64): 

curl -fsSL https://raw.githubusercontent.com/lordbasex/sentineldesk/main/install.sh \
  | sudo bash -s auto

auto picks Docker when it is present and a native systemd install otherwise; docker or native choose explicitly. A running binary can also hand its files to another machine: sentineldesk -install serves them over HTTP and sentineldesk -extract-deploy <dir> writes them to disk.

Every build knows what it is: sentineldesk -version prints something like sentineldesk v1.2.3 (081b14d) · build 20260804-190000, and the same string appears at the bottom of the control rail.

For development, from a clone

make up     # build the image and start the desktop
make logs   # follow the logs
make shell  # a root shell inside the container
make down   # stop everything

Then http://localhost:8080. With AUTH_USER and AUTH_PASS set it asks for a login; without them it is open, and that is for development only.

Production

Pick the compose file that matches the server's hardware. All three use network_mode: host for a direct ICE connection, which is the lowest latency. 

# CPU only (software VP8)
AUTH_USER=admin AUTH_PASS=secret \
docker compose -f deploy/docker-compose.cpu.yml up -d

# NVIDIA GPU (NVENC) — needs nvidia-container-toolkit
AUTH_USER=admin AUTH_PASS=secret \
docker compose -f deploy/docker-compose.nvidia.yml up -d

# Intel/AMD GPU (VA-API) — passes /dev/dri through
AUTH_USER=admin AUTH_PASS=secret \
docker compose -f deploy/docker-compose.vaapi.yml up -d

Before exposing it to the internet, always set AUTH_USER and AUTH_PASS: the production compose files require them. Without them authentication is disabled, which is good for a development LAN and for nothing else.

TLS and certificates

Two ways to serve HTTPS, depending on whether you have a proxy in front.

A. Native TLS in the backend

No Caddy, a single port.

Variables Result
TLS_SELFSIGNED=1 Generates a self-signed certificate once and persists it in the volume. SANs: localhost, the hostname, plus whatever you add in TLS_HOSTS=ip,domain. Good for a LAN or for testing.
TLS_CERT + TLS_KEY Uses your own certificate: a purchased wildcard, a corporate one, or one issued by certbot. Copy the files into deploy/certs/, which is mounted as /certs. 
TLS_SELFSIGNED=1 docker compose -f deploy/docker-compose.yml up -d
# → https://localhost:8080

B. Caddy as a reverse proxy

With --profile tls on the production compose files, choosing the mode with TLS_MODE=.

Mode Certificate Requires
auto Let's Encrypt automatically (HTTP-01), renewing itself DOMAIN pointing at the server, ports 80/443
selfsigned Self-signed by Caddy's internal CA Nothing: works by IP or local name
custom Your certificate / wildcard from deploy/certs/ The files in deploy/certs/
wildcard Let's Encrypt wildcard *.domain (DNS-01 through Cloudflare) An image with the plugin + CLOUDFLARE_API_TOKEN 
# Classic Let's Encrypt
DOMAIN=desktop.example.com AUTH_USER=admin AUTH_PASS=secret \
docker compose -f deploy/docker-compose.nvidia.yml --profile tls up -d

# Self-signed through Caddy (no domain)
TLS_MODE=selfsigned AUTH_USER=admin AUTH_PASS=secret \
docker compose -f deploy/docker-compose.cpu.yml --profile tls up -d

In any of these modes the WebSocket switches to wss:// on its own. Ports to open in the firewall: 80/443 for the web, and WebRTC's UDP range (or the fixed one you set with WEBRTC_MIN_PORT / WEBRTC_MAX_PORT).

Connecting an agent over MCP

The bridge runs inside the container, so the AI host launches it with docker exec. In the host's MCP configuration: 

{
  "mcpServers": {
    "sentineldesk": {
      "command": "docker",
      "args": [
        "exec", "-i", "-u", "sentineldesk", "sentineldesk",
        "/usr/local/bin/sentineldesk", "-mcp-stdio",
        "-mcp-sock", "/run/user/1000/sentineldesk-mcp.sock"
      ]
    }
  }
}
  • -i keeps stdin open: that is the MCP transport.
  • -u sentineldesk runs as the socket's owner (uid 1000).
  • The container has to be named sentineldesk, or adjust the name.

To hand an agent a read-only endpoint against the same daemon you use with full permissions, add -mcp-policy readonly to those arguments. A connection can drop below the ceiling the daemon set, never raise it.

Getting it running, end to end

  1. Start the desktop

    Whichever compose file matches the hardware, with AUTH_USER and AUTH_PASS set.

  2. Open it in the browser

    Port 8080 by default. Whoever arrives first takes control; the rest watch and can ask for it.

  3. Add TLS if it faces the internet

    Native TLS with TLS_SELFSIGNED=1, or Caddy with --profile tls and a domain.

  4. Plug the agent in

    The MCP bridge over docker exec, with whatever policy you want to give it.
