SentinelDesk

A collaborative operating system for people and AI agents. One Linux desktop, in a container, that both of them drive — seeing the same screen, taking turns, and reading each other's errors.

The second half of that is not a metaphor for an API. It is the same X display, the same session, the same room:

  • The agent is a participant, not a background process. It has a name in the list and a pointer on screen in its own colour, so it is never ambiguous whether a colleague or the model just moved the mouse.
  • They take turns. Control is claimed, never assumed — by anybody, agent included, and whether or not somebody is watching. Nobody holds the controls until they ask, so joining to watch does not hand you a desktop you did not want. When somebody is driving, asking puts a prompt on their screen and no answer means no.
  • They read the same state. Every command run in a terminal reports its exit status, whoever ran it, so a person can hit an error and ask the agent to look at what actually happened.
  • One capture, many observers. The desktop is encoded once and fanned out: to every browser, to the recorder, to a live stream. A second participant costs bandwidth, not CPU.

People drive it through a control layer in the browser. The agent drives it through a local socket with 120 MCP tools. Neither is a guest of the other.

Read Installing it and The control layer. Everything else is a reference you can come back to.

What it is built on

A single Go binary. GStreamer runs inside the process through go-gst rather than as a child of it, so the encoder stays reachable at runtime — bitrate follows the network, keyframes answer a request, and an external destination attaches without stopping anything.

Installing and running it

Everything runs in one container. There is nothing to install on the machines that connect to it — a browser is the client.

What you need

  • Docker with Compose v2. Docker Desktop on macOS and Windows, Docker Engine on Linux.
  • 2 GB of RAM and two cores for a comfortable 1080p30. A GPU is optional and changes a lot — see Hardware acceleration.
  • /dev/uinput on the host if you want the browser's gamepad to reach the desktop. Without it everything else still works.
  • amd64 for Steam and Wine, which are in the full image only. Everything else runs on arm64 too, in both images.

Three ways to start it

The repository ships a compose file that also brings up a TURN server, which macOS and Windows need to establish the connection at all.

git clone https://github.com/lordbasex/sentineldesk.git
cd sentineldesk
make up

make up builds both image variants and starts the lite one — see the two images below. Without make:

docker compose -p sentineldesk -f deploy/docker-compose.yml up -d --build

Always pass -p sentineldesk. Compose otherwise names the project after the directory holding the file, and moving the repository would orphan the running containers and hide the persistent home behind a fresh, empty volume.

Smaller, for a quick look. No TURN, so it works over a LAN or on Linux but may fail to connect through a restrictive NAT.

docker run -d --name sentineldesk \
  -p 8080:8080 -p 59000-59049:59000-59049/udp \
  -e AUTH_USER=admin -e AUTH_PASS=change-me \
  -e WEBRTC_MIN_PORT=59000 -e WEBRTC_MAX_PORT=59049 \
  -v sentineldesk-home:/home/sentineldesk \
  --device /dev/uinput --shm-size 2g \
  --cap-add NET_ADMIN --device /dev/net/tun \
  sentineldesk:latest

The UDP range is what WebRTC's media travels over. Publishing it and pinning it with the two variables is what makes the connection work without host networking.

The last two lines are what the VPN client needs: a tunnel device, and the capability to configure routes. Without both, OpenVPN installs fine and then fails at the moment somebody actually needs it. Drop them on a deployment that will never dial a VPN — NET_ADMIN lets the container manage its own network stack, which is a real grant.

Where seccomp=unconfined went

Earlier versions of this page passed --security-opt seccomp=unconfined, and the compose files set it too. Neither does any more. It was there for Steam, whose bootstrap needs user namespaces that Docker's default profile blocks, and Steam is only in the full image on amd64. It widens what the container may ask of the kernel, which is not a thing to leave switched on for a feature most installations never start.

It has one other effect worth knowing, in the opposite direction: with it, Chromium keeps its own sandbox. The container tests for user namespaces at startup and adds --no-sandbox only when they are missing, so the default is an unsandboxed browser — as it always was. Neither the DevTools protocol nor the accessibility tree changes either way, so the browser_* and ui_* tools behave the same.

To change the code. The image is built from the repository root so the Dockerfile can reach both the Go sources and the desktop assets.

# a fast type check on the host, no container involved
go build ./...
# build both variants
make image
# or just one of them
make image-lite
make image-full
# or, without make — note the --target
docker build -f deploy/Dockerfile --target desktop -t sentineldesk:latest .

--target desktop is not optional. The Dockerfile's last stage is full, so leaving it out builds LibreOffice, Firefox, GIMP, Wireshark and the rest — around 2.5 GB — and then tags that as sentineldesk:latest, a name that means lite everywhere else.

The web interface is embedded with go:embed, so editing anything under internal/webui/assets/ means rebuilding the image — the change does not appear by reloading the page.

The two images

One Dockerfile produces both. Lite is the default and is what :latest points at:

TagAlsoWhat it is
sentineldesk:<version>-lite :latest, :lite The desktop and the tools somebody needs in it. The default
sentineldesk:<version>-full :full Adds LibreOffice, Firefox, GIMP, Wireshark, a compiler toolchain and Go; on amd64 also Steam and Wine

To run full instead, build it and point at that tag — with docker run it is one word, and with compose it is the image: line in the file:

make image-full
docker run -d --name sentineldesk … sentineldesk:full
Full is built on top of lite

So everything in one is in the other, and the two share every layer up to the split: a machine that already has lite downloads only the difference. What is installed goes through what each one carries and why.

On a machine of its own — a VPS or a Raspberry Pi

The three ways above assume a clone of the repository. For a machine that will just run this — a VPS, a Raspberry Pi 5 — there is an installer, and it needs nothing checked out.

On a bare install, get curl first. A Debian netinstall with only standard utilities has no curl, and the command below begins with it — the installer can fetch its own dependencies, but not the thing needed to fetch the installer:

All of this has to run as root — it installs packages, writes to /etc and registers a service. If you are logged in as an ordinary user, become root first; your prompt changes from $ to #, and that # is how you know it worked:

sudo su          # or: su -    on a machine whose account cannot use sudo

# and now, with a prompt ending in #
apt update && apt install -y curl

# sudo itself, if this machine does not have it
apt install -y sudo

ca-certificates comes with curl and does not need naming; without it the HTTPS download would fail. Everything else the installer needs it installs itself.

# as root
curl -fsSL https://raw.githubusercontent.com/lordbasex/sentineldesk/main/install.sh \
  | bash -s auto

# from an ordinary account instead, letting sudo do it
curl -fsSL https://raw.githubusercontent.com/lordbasex/sentineldesk/main/install.sh \
  | sudo bash -s auto

The two are the same install; use whichever matches the prompt you are looking at. Run it without root and it stops immediately and prints both lines back at you rather than failing halfway through.

auto picks Docker where it is already installed and a native systemd install otherwise. Say which you want instead, and add the variant — lite is the default:

sudo ./install.sh docker lite    # container + compose, easy to remove
sudo ./install.sh native lite    # systemd + supervisor, straight on the host
sudo ./install.sh docker full    # the larger image
OptionWhat it does
--version vX.Y.ZInstall that release instead of the latest
--binary PATHUse a binary you already have instead of downloading one
--user NAMENative only: run the desktop as an account that already exists, rather than creating a dedicated one

It downloads one artifact — the binary — and verifies it against the release's SHA256SUMS.txt. Everything else it asks the binary for.

The binary is its own distribution

The compose files, the supervisor configuration and the desktop scripts are embedded in it, so configuration and code can never disagree about versions — they were built together. sentineldesk -extract-deploy <dir> writes that tree to disk, which is what the installer uses, and sentineldesk -install serves it over HTTP so another machine can install from this one. sentineldesk -version says exactly what a build is, and the same string appears at the bottom of the rail.

An installed machine comes up on HTTPS with a self-signed certificate, and the certificate names the addresses that machine actually answers on. That last part matters more than it sounds: a VPS is reached by IP, and a certificate that does not name the IP turns a warning you can click through into an error you cannot. The browser still warns once, because self-signed means nobody vouched for it — see trusting it. Set TLS_SELFSIGNED=0 for plain HTTP on a network you trust.

The installer ends with everything needed to use what it just installed: the version, every address this machine answers on — a Raspberry Pi on Ethernet and Wi-Fi at once has more than one, and only you know which your laptop can reach — and the login to type at it.

Credentials are generated on the first install and live in /etc/sentineldesk/env for a native install and /opt/sentineldesk/.env for a Docker one, both readable only by root. That file is written once and then belongs to you: change the login there and restart. The closing summary reads it back rather than remembering what it generated, so re-running the installer prints the current login again — which is also how to recover one nobody wrote down.

A certificate nobody has to click through

Self-signed warns every visitor, every time. For anything with an audience you want a real certificate, and --tls-domain installs Caddy in front and gets one from Let's Encrypt:

sudo ./install.sh native lite \
  --tls-domain desk.example.com --tls-email you@example.com

Renewal is the reason, more than the certificate. Let's Encrypt issues for 90 days and renews at 60, and this server reads its certificate once when it starts — so doing this by hand means copying files and restarting every two months, forever, with a script that fails quietly leaving an expired site. Caddy renews and reloads on its own.

It needs a name, not an IP

Let's Encrypt validates a name: no challenge can prove you control a bare address, so --tls-domain 203.0.113.45 is refused outright rather than failing later. If you have no domain, a wildcard DNS service gives you one that points at your address for nothing — 203-0-113-45.sslip.io — and Let's Encrypt certifies that happily. Ports 80 and 443 have to reach the machine, or validation cannot complete: journalctl -u caddy -f says so if it does not.

With Caddy in front the desktop stops serving TLS itself and binds to the loopback only, so port 8080 is no longer reachable from outside — a proxy the traffic can walk around is decoration. That is HTTP_ADDR, and the installer sets it. WebRTC media is untouched: it travels over its own UDP range, direct, not through the proxy.

Updating is the same command

Run the installer again. It downloads the current release over the old one, rewrites the configuration, restarts the service, and says which way it moved:

▶ updated: v1.1.2 (5d0ed66)  →  v1.1.3 (abc1234)
▶ reinstalled v1.1.3 (abc1234) (unchanged)

Your credentials survive, because that file is only written when it is not already there — and so do any wallpapers you put in yourself.

On a Raspberry Pi, use 64-bit Raspberry Pi OS

The installer takes arm64; 32-bit Raspberry Pi OS reports armv7l and is refused. A Pi 5 has no hardware H.264 encoder — the Pi 4's was dropped — so the picture is encoded by the CPU in software. Lower DISPLAY_WIDTH, DISPLAY_HEIGHT and FPS before deciding it is slow; 720p is a realistic place to start. On a native install those live in /etc/sentineldesk/env.

The first run

Open http://localhost:8080. With AUTH_USER and AUTH_PASS set it asks for a login; without them it is open.

# follow the desktop's logs
make logs
# a root shell inside the running container
make shell
# stop everything
make down

The desktop keeps its home in a named volume, sentineldesk-home, so browser profiles, installed applications and the Steam library survive a restart or a rebuild.

Before putting it on the internet

Set AUTH_USER, AUTH_PASS and a fixed AUTH_SECRET, and serve it over TLS. See Production.

The resolution is not the binary's to change

DISPLAY_WIDTH and DISPLAY_HEIGHT are read by Xvfb when it starts, not by the server. That is why the desktop can be resized smaller at runtime but never larger than what was reserved at boot — and why changing them means restarting the container.

  /usr/local/bin/sentineldesk -mcp-stdio \
  -mcp-sock /run/user/1000/sentineldesk-mcp.sock \
  -mcp-policy safe -mcp-deny 'ssh_*,install_packages'

Hardware acceleration

The encoder is chosen at startup by running a real probe pipeline for each candidate in turn, so what you get reflects what actually works on that host rather than what the drivers claim. Force one with ENCODER=nvenc|vaapi|h264|vp8.

The production compose files differ only in how they reach the GPU. They all use network_mode: host, which gives ICE a direct path and the lowest latency.

Needs nvidia-container-toolkit on the host. Encodes with NVENC, which leaves the CPU almost free and makes 1080p60 realistic.

AUTH_USER=admin AUTH_PASS=secret \
docker compose -f deploy/docker-compose.nvidia.yml up -d

Passes /dev/dri through and encodes with VA-API.

AUTH_USER=admin AUTH_PASS=secret \
docker compose -f deploy/docker-compose.vaapi.yml up -d

Software x264. Fine for 1080p30 on a couple of modern cores; 60 fps is not worth asking for.

AUTH_USER=admin AUTH_PASS=secret \
docker compose -f deploy/docker-compose.cpu.yml up -d
Why x264 and not VP8 without a GPU

Measured on desktop content, libx264 at veryfast carries 1080p for roughly a third of what vp8enc needs, and H.264 is what every browser decodes in hardware. That matters on the receiving side too: a client that cannot keep up looks like a congested network to the congestion estimator, and drags the whole room's bitrate down.

Production

The security model

It is short enough to state in one line: the WebSocket is the only door.

The first WebSocket frame has to be an authentication frame with a username and password, or a session token. Until it validates there is no WebRTC handshake at all — no SDP offer, no ICE, no DataChannel. An invalid token, an offer trying to skip authentication, or silence past the ten-second deadline closes the connection.

Repeated failures from one origin are rate-limited and then banned for a while, so a password is not something that can be guessed at speed.

  • Set AUTH_SECRET to a fixed value. Left unset it is random, and every restart invalidates everyone's session.
  • FILES_ROOT bounds what the file manager can reach. Leave it inside the home unless you mean otherwise.
  • Downloads travel with a one-time ticket in the URL rather than the session token, so a link that leaks is already spent.
  • The MCP socket is 0600 and local to the container. It is never exposed over the network.

TLS

Two ways, depending on whether something else sits in front.

No proxy, one port. A self-signed certificate is generated once and kept in the volume:

TLS_SELFSIGNED=1 docker compose -f deploy/docker-compose.yml up -d

Add the addresses people will actually type, or the certificate will not match them:

TLS_SELFSIGNED=1 TLS_HOSTS=192.168.1.50,desktop.local \
docker compose -f deploy/docker-compose.yml up -d

With a certificate of your own — a purchased wildcard, a corporate one, one from certbot — copy fullchain.pem and privkey.pem into deploy/certs/:

TLS_CERT=/certs/fullchain.pem TLS_KEY=/certs/privkey.pem \
docker compose -f deploy/docker-compose.yml up -d

The production compose files carry a Caddy profile. Pick the mode with TLS_MODE.

# Let's Encrypt, renewing itself. Needs DOMAIN pointing here and ports 80/443
DOMAIN=desktop.example.com AUTH_USER=admin AUTH_PASS=secret \
docker compose -f deploy/docker-compose.nvidia.yml --profile tls up -d

# Self-signed by Caddy's own CA — works by IP, no domain needed
TLS_MODE=selfsigned AUTH_USER=admin AUTH_PASS=secret \
docker compose -f deploy/docker-compose.cpu.yml --profile tls up -d

# Your own certificate from deploy/certs/
TLS_MODE=custom DOMAIN=desktop.example.com AUTH_USER=admin AUTH_PASS=secret \
docker compose -f deploy/docker-compose.cpu.yml --profile tls up -d

A Let's Encrypt wildcard needs the DNS-01 plugin, which means building Caddy with it:

docker build -t caddy-cloudflare -f deploy/Dockerfile.caddy deploy
CADDY_IMAGE=caddy-cloudflare TLS_MODE=wildcard DOMAIN=example.com \
CLOUDFLARE_API_TOKEN=xxxx AUTH_USER=admin AUTH_PASS=secret \
docker compose -f deploy/docker-compose.cpu.yml --profile tls up -d

In every mode the client switches to wss:// on its own.

TURN is not optional on macOS and Windows

Docker Desktop runs the container inside a VM, so the addresses ICE discovers are the VM's and not reachable. The relay is what closes that gap; the development compose file starts one for exactly this reason.

Certificates

Four ways to get one, from least to most work. All of them end with the same thing: a fullchain.pem and a privkey.pem the server reads.

The built-in one

TLS_SELFSIGNED=1 and there is nothing else to do. On first start the server generates an ECDSA P-256 certificate valid for 825 days — the longest a browser will accept — and writes it to /home/sentineldesk/.tls/, which is inside the persistent volume, so it survives restarts and rebuilds. If the files are already there it uses them and generates nothing.

It covers localhost, 127.0.0.1, ::1 and the container's hostname. That is enough to open it on the machine running Docker and no further — a browser checks the address you typed against the names in the certificate, and a LAN IP that is not in there fails even though the certificate is otherwise fine. Add them:

TLS_SELFSIGNED=1 TLS_HOSTS=192.168.1.50,desktop.local \
docker compose -p sentineldesk -f deploy/docker-compose.yml up -d

To regenerate — after adding a name, or because it expired — delete the two files and restart. Nothing else is cached:

docker exec sentineldesk rm -f /home/sentineldesk/.tls/cert.pem \
                              /home/sentineldesk/.tls/key.pem
make down && make up
The browser will warn

Self-signed means nobody vouched for it, and that is exactly what the warning says. Advanced → Continue works, but you will see it every time — see below for making it stop.

Trusting it, so the warning stops

Take a copy of the certificate out of the container:

docker cp sentineldesk:/home/sentineldesk/.tls/cert.pem ./sentineldesk.pem

Then add it to the machine you browse from — not to the server:

sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain sentineldesk.pem

Restart the browser afterwards. Firefox keeps its own store and has to be told separately, in its settings.

sudo cp sentineldesk.pem /usr/local/share/ca-certificates/sentineldesk.crt
sudo update-ca-certificates

Chrome on Linux uses NSS rather than the system store, so it may also need certutil -d sql:$HOME/.pki/nssdb -A -t "C,," -n sentineldesk -i sentineldesk.pem.

In an elevated PowerShell:

Import-Certificate -FilePath .\sentineldesk.pem `
  -CertStoreLocation Cert:\LocalMachine\Root
mkcert, if this is a machine you develop on

mkcert installs a local authority once and then issues certificates your browser already trusts, with no warning to click through:

mkcert -install
mkcert -cert-file deploy/certs/fullchain.pem \
       -key-file  deploy/certs/privkey.pem \
       desktop.local 192.168.1.50 localhost

Then use it as your own certificate, below.

A certificate you already have

A purchased wildcard, one your organisation issues, one from certbot. Copy the two files into deploy/certs/, which the compose file mounts read-only at /certs:

cp fullchain.pem privkey.pem deploy/certs/
TLS_CERT=/certs/fullchain.pem TLS_KEY=/certs/privkey.pem \
docker compose -p sentineldesk -f deploy/docker-compose.yml up -d

fullchain.pem has to be the full chain — your certificate followed by the intermediates. A leaf on its own validates in a browser that happens to have the intermediate cached and fails everywhere else, which makes for a confusing afternoon.

To make one yourself, for a name that is not public:

openssl req -x509 -newkey rsa:2048 -nodes -days 825 \
  -keyout privkey.pem -out fullchain.pem \
  -subj "/CN=desktop.local" \
  -addext "subjectAltName=DNS:desktop.local,IP:192.168.1.50"

The subjectAltName is not optional. Browsers stopped looking at the common name years ago, and a certificate without SANs is rejected outright.

Let's Encrypt

For a name that resolves publicly. The simplest route is the Caddy profile, which obtains and renews on its own:

DOMAIN=desktop.example.com AUTH_USER=admin AUTH_PASS=secret \
docker compose -p sentineldesk -f deploy/docker-compose.cpu.yml --profile tls up -d

It needs DOMAIN pointing at this server and ports 80 and 443 reachable from the internet — the HTTP-01 challenge is Let's Encrypt connecting back to you.

With certbot instead, and feeding the result to the backend directly:

certbot certonly --standalone -d desktop.example.com
cp /etc/letsencrypt/live/desktop.example.com/fullchain.pem deploy/certs/
cp /etc/letsencrypt/live/desktop.example.com/privkey.pem   deploy/certs/

Certbot renews every 60 days but the server reads the certificate at startup, so a renewal hook has to copy the files again and restart the container. The Caddy profile exists to avoid exactly this.

A wildcard

One certificate for *.example.com. Let's Encrypt only issues wildcards through the DNS-01 challenge, which means Caddy needs the plugin for your DNS provider compiled in:

docker build -t caddy-cloudflare -f deploy/Dockerfile.caddy deploy
CADDY_IMAGE=caddy-cloudflare TLS_MODE=wildcard DOMAIN=example.com \
CLOUDFLARE_API_TOKEN=xxxx AUTH_USER=admin AUTH_PASS=secret \
docker compose -p sentineldesk -f deploy/docker-compose.cpu.yml --profile tls up -d

The token needs permission to edit that zone's DNS records, and nothing more.

Which to use

SituationUse
Your own machine, trying it outNo TLS at all, or TLS_SELFSIGNED=1
A LAN, several peoplemkcert, or self-signed with TLS_HOSTS and trusted once
A public nameCaddy with TLS_MODE=auto
A certificate the organisation issuesTLS_CERT / TLS_KEY, or TLS_MODE=custom
Several subdomainsTLS_MODE=wildcard

Updating and state

Rebuilding replaces the image; it does not touch the home.

git pull
make up

What survives lives in the named volume sentineldesk-home: browser profiles, applications you installed, the Steam library, the self-signed certificate. What does not is anything written outside the home inside the container — that goes with the old image.

To start over, and lose all of it:

make down
docker volume rm sentineldesk-home
A rebuilt image but the old interface

That should not happen: the client is served with an ETag over its own bytes, so the browser has to revalidate. If it does, confirm the container was recreated rather than restarted — make up rebuilds and recreates.

The control layer

Everything you operate lives in a rail on the left of the browser window. It floats over live video of a real desktop, so it is deliberately frosted rather than solid: what it covers is desktop you stop seeing.

Press º to show and hide it. That key never reaches the remote desktop.

GroupWhat is in it
CaptureMicrophone, screenshot, recording, stream out
SessionFiles, audio on/off, statistics
ViewerFull screen, language

Windows of this layer — the file manager, statistics, streaming — stay open while you use the rail, can be dragged by their title bar, and close only from their own ×. Double-clicking the title bar re-centres one that ended up somewhere awkward.

Sharing the session

One desktop, several participants. The model is a shared console: exactly one participant holds control at a time and everyone else watches. The capture is encoded once and sent to all of them, so a second viewer costs bandwidth, not CPU.

Taking and releasing control

The presence panel at the top of the rail says which of three states you are in: you are driving, somebody else is, or nobody is. Control is cooperative between people — anyone may take it, and whoever had it sees the change immediately. There is no hierarchy, because everyone got in with the same credential.

Joining does not give you the controls. The desktop starts with nobody driving and stays that way until somebody asks, so opening it to watch a colleague work is a thing you can do without taking the machine out from under them. Press Take control when you actually want it.

Releasing frees the controls; it does not hand them to the next person. "I have finished" and "you are up now" are different statements, and only the first one is ever true. The same holds if the person driving simply closes their tab: the controls go free rather than landing on whoever happens to have been there longest.

The floating bar

A bar at the bottom of the screen tells everyone which way things stand, and it carries the button: green when the controls are free, amber when somebody else is driving. It stays for as long as that is true instead of flashing past — the moment the agent finishes a task is exactly when you might be looking somewhere else.

The AI agent's turn

The agent is a participant like any other: a name in the list and a pointer on screen in its own colour, so it is never ambiguous whether a colleague or the model just moved the mouse.

The rule is one line: control is claimed, never assumed. That holds for the agent whether or not anybody is watching — an empty room used to be a free pass, and it is not one any more. Asking costs the agent nothing when the controls are free, because the answer comes back immediately; what it buys is a room that always knows who has the desktop. When somebody IS driving, the agent has to ask them — a prompt appears on your screen with a draining timer, and no answer means no.

Reading each other's errors

Every command run in a terminal on this desktop reports its exit status, whoever ran it. So a person can hit an error, ask the agent to look at it, and the agent reads what actually happened instead of being told about it second-hand.

Screenshots and recording

Both are in the Capture group, and both go through the server rather than the browser. That means the file comes out at the framebuffer's own quality, without the stream's compression — and as MP4, which opens on any operating system with nothing installed. WebM and MKV are available too.

Other participants' pointers are drawn onto the X display itself, so they appear in screenshots and recordings the same way they appear on screen.

Streaming the desktop out

Stream out in the Capture group sends the live session somewhere else: YouTube, Twitch or Facebook with just a stream key, or a full address for a VLC or OBS you run yourself.

It reuses the encode the room is already producing. Going live does not interrupt what anyone is watching, and an extra destination costs a muxer and a socket rather than a second capture of the screen. The multiplier that is real is bandwidth: each destination carries the full stream out of the machine.

Whoever holds control decides, and everyone in the room sees the destination list — a session being broadcast is not something to find out about afterwards. Stream keys are redacted before they reach any browser or log.

YouTube, Twitch, Facebook

Pick the platform and paste only the stream key. The ingest address is already known, so there is nothing to look up.

Watching it in VLC

Two steps, in this order: start VLC listening first, then press Go live. If nothing is listening, the desktop has nowhere to send to.

Step 1 — put VLC in listening mode on your own machine:

VLC installs no vlc command; call the binary inside the application.

"/Applications/VLC.app/Contents/MacOS/VLC" \
  --network-caching=200 "udp://@:5000"
vlc --network-caching=200 "udp://@:5000"

From PowerShell or the command prompt:

"C:\Program Files\VideoLAN\VLC\vlc.exe" ^
  --network-caching=200 "udp://@:5000"

The @ is what makes VLC listen instead of connect — without it, nothing happens and no error is printed. --network-caching=200 drops VLC's own buffer from one second to 200 ms; leave it out and you will blame the streaming for a delay that is VLC's.

You can check it really is listening:

# Linux / macOS — should show UDP *:5000, not a random high port
lsof -nP -iUDP:5000

Step 2 — in the panel, choose VLC / OBS and enter the address:

Where Docker runsAddress to use
Docker Desktop, same machine as VLC (macOS, Windows) udp://host.docker.internal:5000
Docker on Linux, same machine as VLC udp://172.17.0.1:5000
A different machine udp://<that machine's IP>:5000

Leave Viewers can join mid-stream unchecked. It is your own receiver — it does not need a keyframe every two seconds, and the bits saved go back into keeping text readable.

Why udp:// and not srt:// for VLC

VLC 3 speaks SRT only as a caller: it can connect out, but it cannot receive a connection, and ?mode=listener is silently ignored. Point SentinelDesk at it over SRT and both sides end up calling, neither answers, and nothing is logged because nothing failed. Use udp:// for VLC.

Watching it in OBS

Add a Media Source, untick Local File, and put the same udp://@:5000 in the input box. OBS is happy with srt:// too, in listener mode.

Which protocol to use

SchemeUse it for
udp://A player on your network. Works everywhere, nothing to negotiate.
srt://A receiver over the internet that listens: an SRT server, OBS in listener mode. Recovers from packet loss; pointless on a LAN.
rtmp://, rtmps://The platforms. Elderly and awkward, and the only thing they accept.

About keyframes

A viewer cannot see anything until a keyframe arrives, so a platform serving an audience that turns up at arbitrary moments needs one every two seconds. That is enforced automatically while such a destination is connected, and it goes back to on-demand the moment the last one stops.

Keyframes are ten to fifty times the size of a normal frame, and every bit they take is a bit not spent on the text on your screen. A receiver you start yourself can simply wait for the first one, which is why it gets a sharper picture.

H.264 only

No streaming destination accepts VP8. Encoder auto-detection prefers x264 over VP8, so this is normally already true; on a host where it is not, set ENCODER=x264.

The address is remembered

What you type is kept in this browser, per destination, so reopening the panel mid-stream shows what is being sent and stopping does not mean pasting a stream key again. It is stored the way a browser stores a password: on this machine, for this site, and nowhere else.

Moving files

Files in the Session group opens a two-pane manager: the remote desktop on the left, your own machine on the right. Function keys along the bottom do the usual things — F5 copy, F6 rename, F7 new folder, F8 delete, F2 refresh.

You can also drop files anywhere on the page to send them to the desktop, without opening the manager at all.

Downloads travel with a one-time ticket in the URL rather than your session token, so a link that leaks is spent and useless. FILES_ROOT bounds what the manager can reach.

Your microphone, on the desktop

Microphone in the Capture group sends your microphone into the container, where applications see it as a real input device — not as a monitor of something playing, which browsers hide from their microphone pickers. Right-click the button to choose which microphone.

Only the participant holding control may publish audio.

The AI agent

SentinelDesk exposes 120 tools over a local Unix socket using the Model Context Protocol. An AI host — Claude Code, Claude Desktop, or anything else that speaks MCP — connects through a thin bridge:

docker exec -i sentineldesk sentineldesk -mcp-stdio

Killing the AI host does not take the desktop down with it. The socket is 0600 and local to the container.

Connecting one

The bridge is a sub-command of the same binary, run through docker exec. In your MCP client's configuration:

{
  "mcpServers": {
    "sentineldesk": {
      "command": "docker",
      "args": [
        "exec", "-i", "-u", "sentineldesk", "sentineldesk",
        "/usr/local/bin/sentineldesk", "-mcp-stdio",
        "-mcp-sock", "/run/user/1000/sentineldesk-mcp.sock"
      ]
    }
  }
}

-i keeps stdin open, which is the transport; -u sentineldesk runs as the socket's owner.

The tools cover the mouse and keyboard, windows, running commands, screenshots and recording, the browser through DevTools, the accessibility tree — so the agent can read what is on screen as structure rather than as pixels — files, packages, SSH, and the room itself.

Finding the right tool

A hundred and twenty tool descriptions is a real amount of a model's attention, spent before it has read your request. tool_search is the way around it: describe the task and get back the handful of tools that do it, with their input schemas attached so they can be called straight away.

{"name": "tool_search", "arguments": {"query": "give someone remote access"}}

That returns the ssh_* tools, ranked, each with its risk level and its schema. Ask for a whole theme instead with {"category": "ssh"} — the themes are ssh, shell, terminal, browser, accessibility, windows, input, screen, files, processes, packages, snapshot, recording, restream, room, audio, clipboard, desktops, gamepad, system and general.

Searching only saves anything if something is not being listed in the first place, and most AI hosts already handle that themselves — Claude Code defers tool schemas and loads them on demand. For hosts that do not, set MCP_DISCOVERY=1: the tool list then advertises a core set of twelve — enough to look at the desktop, read its structure, click, type and run something — and leaves tool_search to surface the rest.

Every other tool stays callable. Discovery narrows what is advertised, never what is permitted; that is the policy's job, below. A tool left out of the list is one the agent has not been told about yet, not one it is forbidden to use.

Limiting what it may do

Every tool declares what it can do to the machine, and the policy levels are built on that one declaration:

RiskWhat it meansExample
readObserves; changes nothing screenshot, ui_tree
writeDrives the desktop — input, windows, volume, the clipboard — but cannot reach the system underneath mouse_click, type_text
dangerRuns code, touches the system, or moves data outwardrun_command, ssh_exec
VariableEffect
MCP_POLICY=fullEverything (default)
MCP_POLICY=safeRemoves the danger tools — those that run code or touch the system
MCP_POLICY=readonlyOnly the read tools
MCP_DENY / MCP_ALLOWPatterns, for finer control
MCP_DISCOVERY=1Advertise only the core set and let tool_search find the rest. Not a permission — see above

A connection may restrict itself further, but never widen — which is what makes it safe to hand an agent a read-only endpoint without changing anyone else's.

The risk levels are also published as the Model Context Protocol's own readOnlyHint and destructiveHint annotations, so an AI host that understands them can decide on its own when to ask you before acting — without knowing anything about SentinelDesk.

What is installed, and the two images

Two variants come out of one build. Lite is the default; full adds what is too large or too specialised to hand everybody.

Lite here does not mean headless — on a Raspberry Pi that is what "Lite" means, but here the desktop is the product. It means the smallest set that leaves nobody reaching for a package manager on their first afternoon: a browser, a text editor, image and document viewers, an archive manager, a calculator and a task manager, plus the network toolbox this desktop mostly exists to use — nmap, dig, iperf3, tcpdump, mtr, sngrep and an OpenVPN client. Git is there too, because everybody clones something.

Full adds LibreOffice, Firefox, GIMP, Wireshark, a compiler toolchain and Go, and on Intel machines also Steam and Wine.

Go sits in full rather than lite deliberately, even though this project is written in it. A toolchain is a quarter of a gigabyte for people who will never type go, and "everybody clones something" is a claim that holds for git and not for a compiler.

Full contains lite

Full is built on top of lite rather than beside it, so everything in one is in the other. It also means the two share almost all their storage: a machine that already has lite downloads only the difference.

Finding things

The menu is grouped by what you want to do. Terminal, Web Browser, Files and Text Editor sit at the top because they are what gets opened every session; Accessories, Network and System Tools hold the rest, and All Applications lists everything installed.

The command-line entries under Network open a terminal with the tool's usage already printed, so you do not have to go and look up the flags first.

Connecting to a VPN

Network → VPN asks for a .ovpn profile and connects. Profiles kept in ~/.openvpn are offered directly, and the home survives restarts, so a connection you set up once stays set up.

This needs the container to have been started with a tunnel device and network privileges. If it was not, the dialog says so and shows the two lines to add rather than failing quietly.

Clock and keyboard

Both are set when the desktop starts, so one image serves every region. The clock follows TZ — any standard name such as America/Argentina/Buenos_Aires — and the keyboard follows KEYBOARD_LAYOUT: us, es for Spain, latam for Latin America, and so on.

If either is spelled wrong it is reported and ignored rather than half-applied. A clock quietly running in UTC because of a typo is worse than one that tells you.

When something is wrong

Nothing arrives at VLC

Almost always one of three things. Check them in this order:

  1. VLC is not actually listening. lsof -nP -iUDP:5000 must show UDP *:5000. A random high port means it is calling out, not listening — you forgot the @.
  2. The address points somewhere the container cannot reach. From inside Docker, localhost is the container itself, and a host address inside 172.17.0.0/16 collides with Docker's own bridge.
  3. You are using srt:// with VLC. See above.

The interface did not change after a rebuild

It should — the client is served with an ETag over its own bytes, so the browser has to revalidate. If it genuinely persists, confirm the container was recreated and not just restarted: make up rebuilds the image.

The picture is soft, or lagging behind

Open Statistics. It shows the live bitrate, frames, packets, how far behind live you are, and a clock down to milliseconds — which is the quickest way to tell whether two browsers are actually in sync.

Software encoding 1080p is the usual cause. Set ENCODER=x264 if auto-detection landed on VP8, and check whether the host has a GPU worth using with nvenc or vaapi.

Keys are not reaching the desktop

Check the presence panel: only the participant holding control sends input. If a window of the control layer is open, the keyboard belongs to it, not to the desktop.
